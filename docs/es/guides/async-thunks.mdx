# Thunks asíncronos

`create_async_thunk(type_prefix, payload_creator)` envuelve una función síncrona o coroutine y despacha actions del ciclo de vida a su alrededor. `configure_store(...)` instala automáticamente el middleware de thunks.

## Define las transiciones de estado

```python
from pydux import create_async_thunk, create_slice

jobs_slice = create_slice(
    name="jobs",
    initial_state={"status": "idle", "result": None, "error": None},
    reducers={},
    extra_reducers={
        "jobs/fetch/pending": lambda state, action: state.update(status="loading", error=None),
        "jobs/fetch/fulfilled": lambda state, action: state.update(status="done", result=action.payload),
        "jobs/fetch/rejected": lambda state, action: state.update(status="failed", error=action.payload),
    },
)

fetch_jobs = create_async_thunk("jobs/fetch", lambda: ["build", "test", "release"])
```

## Despacha el thunk

```python
store.dispatch(fetch_jobs())
```

| Action | Cuándo | Payload |
| --- | --- | --- |
| `jobs/fetch/pending` | El creador del payload comienza. | Primer argumento del thunk, si existe. |
| `jobs/fetch/fulfilled` | Retorna correctamente. | Valor retornado. |
| `jobs/fetch/rejected` | Lanza una excepción. | Mensaje de error. |

La excepción original se vuelve a lanzar después de despachar la action rejected, por lo que quienes realizan la llamada aún pueden manejarla.

## Coroutines

Los creadores de payload pueden ser funciones `async def`. PyDux resuelve su resultado awaitable antes de despachar la action fulfilled.

```python
async def fetch_temperature(sensor_id: str) -> float:
    return await client.read_temperature(sensor_id)

fetch_temperature_thunk = create_async_thunk("telemetry/fetch", fetch_temperature)
store.dispatch(fetch_temperature_thunk("sensor-1"))
```

<Note>
  Los thunks coordinan trabajo y emiten actions; los reducers permanecen como transiciones de estado síncronas. Esta separación mantiene el comportamiento de los reducers determinista y fácil de probar.
</Note>
